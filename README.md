# Customer churn MLOps foundation

An original end-to-end tabular classification project demonstrating Git/DVC data versioning,
configuration-driven training, MLflow experiments, pytest, dependent GitHub Actions jobs,
and Evidently drift monitoring. This is an educational foundation, not a deployed service.

## Dataset
The original synthetic customer churn benchmark is generated by `src/generate_data.py`:
3,000 rows, six numeric features, four categorical features, a binary target, and approximately
3% missing values per feature. Seed 2026 fixes the dataset. Churn depends on contract, tenure,
support calls, late payments, monthly charge, and independent noise. No personal records are used.
Its artificial relationships make infrastructure reproducible; scores do not establish real-world utility.

## Verified local results
All 16 pytest cases passed. Five completed validation experiments selected a forest
with 100 trees, depth 8, and minimum leaf size 2. Its untouched final test split
achieved ROC AUC 0.957983, accuracy 0.878333, and F1 0.872154.
Stable drift share was 0.00; the deliberate shifted scenario detected three of ten
features (0.30) and returned the expected alert exit code 1.

## Setup and data
Use Python 3.12 and run from the repository root:

```sh
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
dvc pull
pytest tests/ -v
```

The training CSV is ignored by Git and tracked only through `data/churn.csv.dvc`.
DVC's default read-only public HTTP remote is hosted at
https://stevensherhouse.github.io/churn-mlops-pipeline using GitHub Pages.
The dataset is generated during deployment and uploaded as a Pages artifact; the raw
CSV and cache objects are never committed to Git. A fresh clone can run `dvc pull`
without credentials. The committed MD5 verifies the data version.

An offline, reproducible local remote is also configured at `dvc-remote/` (ignored):
```sh
python -m src.bootstrap_data
dvc pull -r local
```
Bootstrap recreates the seeded dataset, verifies its MD5, and populates the local remote.
CI uses this local remote so pull requests do not depend on the Pages deployment.

## Train and compare
```sh
python run_experiments.py
python compare_experiments.py
python -m src.train --config configs/best.yaml --final
mlflow ui --backend-store-uri sqlite:///mlflow.db
```

Open http://127.0.0.1:5000 to view the five validation experiments and final test evaluation.
Every run logs flattened YAML settings, the exact CSV MD5 matching the DVC pointer,
ROC AUC (primary), accuracy and F1, and the full preprocessing/model pipeline using
`mlflow.sklearn.log_model`. Comparison uses `mlflow.search_runs`, filters finished validation
runs, and writes `configs/best.yaml` and `reports/experiments.csv`. Runtime stores and
models are ignored; the `v1.0.0` GitHub release contains `mlops-evidence.zip` with
the actual six local runs, logged models and drift HTML reports. Extract it into the
repository root, then launch the MLflow UI using the command above. Relative artifact
locations make the tracking store portable. `reports/experiments.csv` is also committed.

The split is fixed and stratified: 60% training, 20% validation, 20% test. Imputation
and encoding fit only on training rows. Model selection uses validation ROC AUC;
the final test split is used after selection. The small-sample model tests use a fixed
test set for regression protection, so production acceptance should use fresh labeled data.
The gate raises an error and exits nonzero below ROC AUC 0.85, accuracy 0.78, or F1 0.70.

## Monitoring
```sh
python -m src.monitor_drift --scenario stable
python -m src.monitor_drift --scenario drifted
```
The drifted command intentionally exits 1 when drift share exceeds the YAML threshold (0.25).
Reference rows are the training split; production rows are the disjoint test split.
All ten input features are monitored. The target is excluded because production labels may be delayed.
HTML and machine-readable summaries are written to `reports/`. Read `MONITORING.md` for analysis.

## CI and structure
`src/` separates generation, preprocessing, training, evaluation, configuration, and monitoring.
`configs/` holds training/gate/drift settings; `tests/` contains unit, actual-data, and model tests.
The workflow triggers on pushes and PRs to main, plus manual dispatch. The training job
depends on the full test job, enforces all model gates, and uploads model/tracking evidence.
GitHub Actions success must be verified in the published repository; a local test pass is not proof of it.
